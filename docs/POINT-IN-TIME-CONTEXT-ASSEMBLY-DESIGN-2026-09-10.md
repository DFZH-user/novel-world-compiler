# 时点知识与上下文装配方案（待审稿）

> 日期：2026-09-10  
> 状态：待审，不代表已批准实施  
> 约束：本稿只收口总体方案，不修改数据库、不改变现有导出契约、不启动运行时接入。

## 1. 结论

项目不需要推倒重来。现有“原文证据 → 结构化事实 → 人工确认 → 时点投影 → Character Card / World Info 导出”主干正确，尤其是来源定位、修订、指纹、审核状态和可复现导出，应继续作为可信基础。

下一阶段不应再以“增加一种导出格式”为中心，而应补齐一层统一的 **时点知识与上下文装配层**。它回答四个彼此独立的问题：

1. 世界中实际发生了什么？
2. 截止某个场景，读者已经知道什么？
3. 某个角色当时知道、相信、怀疑或误解什么？
4. 某次运行最终把哪些内容交给了模型，为什么？

这四个问题不能继续由 `truth`、`visibility`、`first_revealed_ordinal` 或一个入口段落共同承担。

## 2. 外部产品和研究给出的启发

### 2.1 创作工具的共同做法

- Novelcrafter 将 Codex 作为故事资料中心，并把资料的 AI 使用方式区分为始终加入、检测后加入、不加入和永不加入；它的 Progressions / Additions 还能让人物或设定变化从指定场景开始生效。这说明“内容是什么”“何时生效”“是否允许进入上下文”应是独立维度。参考：[Codex](https://www.novelcrafter.com/help/docs/codex/the-codex)、[Codex entry anatomy](https://www.novelcrafter.com/help/docs/codex/anatomy-codex-entry)、[Codex tracking](https://www.novelcrafter.com/help/docs/codex/codex-tracking)、[Progressions and additions](https://www.novelcrafter.com/help/docs/codex/progressions-additions)。
- SillyTavern 的 World Info 已经支持作用域、关键词触发、优先级、递归、分组和 token 预算；同时它明确提醒向量触发具有不可预测性。它的 Prompt Itemization / Inspector 也说明：用户需要看到最终进入模型的提示词，而不只是看到导出 JSON。参考：[World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)、[Prompts](https://docs.sillytavern.app/usage/prompts/)、[Chat vectorization](https://docs.sillytavern.app/extensions/chat-vectorization/)。
- NovelAI Lorebook 同样把激活、插入位置、优先级和上下文预算作为运行时问题，而不是世界观数据本身的属性。参考：[Lorebook](https://docs.novelai.net/en/text/lorebook/)、[Context settings](https://docs.novelai.net/en/text/editor/advancedsettings/)。

### 2.2 检索与评测的共同做法

- Contextual Retrieval 的实践表明，检索前应给片段补充上下文，并结合语义检索、关键词检索和重排，而不是只依赖 embedding。参考：[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)。
- GraphRAG 区分本地、全局、DRIFT 等查询方式。角色扮演的常态需求更接近“局部实体关系 + 原文片段”，昂贵的全局社区摘要不适合作为默认路径。参考：[GraphRAG query modes](https://microsoft.github.io/graphrag/query/overview/)、[GraphRAG dataflow](https://microsoft.github.io/graphrag/)。
- RAGChecker 强调把检索器和生成器分开诊断；LongMemEval 单独检查时序、信息更新和应当拒答的情况。这正适合本项目的“不能提前剧透”和“旧认知被更新”问题。参考：[RAGChecker](https://arxiv.org/abs/2408.08067)、[LongMemEval](https://arxiv.org/abs/2410.10813)。
- ChatHaruhi、CharacterEval、PersonaEval 和 RoleLLM 说明，原作对话记忆与角色一致性评测有价值，但自动裁判不能直接代替人工金标准，尤其要防止模型凭预训练记忆“猜中”知名角色。参考：[ChatHaruhi](https://arxiv.org/abs/2308.09597)、[CharacterEval](https://arxiv.org/abs/2401.01275)、[PersonaEval](https://arxiv.org/abs/2508.10014)、[RoleLLM](https://arxiv.org/abs/2310.00746)。

## 3. 建议的五层架构

### 3.1 原文与证据层

保留现有段落、文本块、来源跨度、导入批次和修订指纹。这里回答“结论来自哪里”，不直接决定运行时是否可见。

### 3.2 规范知识层

保存人物、地点、事件、关系、属性和断言，以及它们的真实性状态、有效时间和证据。该层表达世界模型，不表达某个角色一定知道它。

### 3.3 时点与认知投影层

把下面三类状态分开：

- `world_truth`：世界真相及其有效区间。
- `reader_disclosure`：某条信息何时向读者或指定叙事频道公开。
- `character_belief`：指定角色在某时点知道、相信、怀疑、不相信或未知的命题。

建议先使用概念模型验证，不立即落数据库迁移。认知断言至少需要：主体角色、所指命题、认知状态、获得来源、有效区间、保密约束和证据。

典型情况必须能准确表达：

- “这是谣言，但角色知道有这个谣言。”
- “这是真相，但只有部分角色知道。”
- “角色相信一条错误信息，并因此采取行动。”
- “读者已经知道，但当前角色仍不知道。”

### 3.4 场景快照层

任意入口不再只是一个 `entry_paragraph`，而是一个可审计的场景快照：

- 场景起止边界与入口锚点；
- 时间、地点、在场人物；
- 入口之前已发生的关键事件；
- 人物当时的状态、关系、目标和冲突；
- 该人物可知、可相信和禁止提前获知的内容；
- 快照依据的投影版本和证据。

边界无法可靠判断时，应显式标记为待审或低置信，而不是自动把入口段落当成完整场景。

### 3.5 运行时上下文装配层

这是规范知识和各类适配器之间新增的统一层。Character Card、SillyTavern World Info、未来 Skill 或其他客户端都只能消费装配结果，不应各自重新解释权限和时序规则。

## 4. 上下文装配流水线

建议固定为以下顺序：

1. 解析场景快照和角色身份。
2. 按时点、主体、可见性和保密策略做前置过滤。
3. 加入简短且稳定的角色核心信息。
4. 加入当前场景的确定性快照。
5. 激活明确规则命中的设定和世界信息。
6. 对剩余长尾知识执行关键词 + 向量混合召回。
7. 扩展必要的局部实体关系和来源片段。
8. 重排、去重、冲突检测和过期信息处理。
9. 按预算桶裁剪，而不是只按总分截断。
10. 生成最终提示词和运行回执。

必须坚持“先权限过滤、再检索”。检索到禁止内容后再删除，既会污染重排，也难以证明没有泄漏。

### 4.1 建议的预算桶

- 角色核心：短、稳定、始终保留。
- 场景快照：当前运行最高优先级。
- 激活设定：确定性规则优先。
- 检索记忆：按相关性动态加入。
- 对话记忆：保留最近交流和必要摘要。

预算不足时，回执必须说明哪个条目因哪个预算桶被舍弃。

## 5. Prompt Receipt（提示词回执）

每次装配都应生成不可变的回执，至少包含：

- 请求身份、场景锚点、角色和策略版本；
- 使用的数据修订、投影版本和适配器版本；
- 候选条目、检索路径、关键词/向量/关系得分；
- 每条内容的纳入或排除原因；
- 冲突、过期、权限和剧透过滤结果；
- 各预算桶的估算 token；
- 实际发送的最终提示词与 API 返回的实际 token（有运行时接入后）；
- 生成物与本次回执的关联。

“导出文件大小”不能替代实际 prompt token；“能生成卡片”也不能证明运行时没有剧透。

## 6. 与现有项目的映射

| 现有能力 | 处理意见 | 缺口 |
| --- | --- | --- |
| 原文段落、文本块、SourceSpan | 直接复用 | 需要与场景边界关联 |
| 修订、指纹、导出检查 | 直接复用 | 运行时策略也需要版本化 |
| 人工确认 / pending 状态 | 直接复用 | 场景和认知断言也要有审核状态 |
| `truth_status` / `truth` | 保留为世界断言属性 | 不能替代角色认知状态 |
| `visibility`、`first_revealed_ordinal` | 保留并收窄语义 | 不能同时代表读者公开、角色知情和运行时权限 |
| `valid_from_ordinal` / `valid_to_ordinal` | 复用时点投影思想 | 关系、认知和状态变化需要统一规则 |
| `StoryKnowledgeProjection` / `story-state-service` | 作为投影基础演进 | 目前主要按入口和受众投影，缺少场景与主体认知模型 |
| Card / Worldbook / Bundle 导出 | 保留为适配器 | 不能成为策略真源 |
| 模型运行的 prompt 版本与 token 记录 | 复用审计思路 | 缺少完整装配候选、排除原因和最终 prompt 回执 |

数据库 schema 暂时保持当前版本。先用合同、夹具和离线回放验证概念边界，批准后再决定是否新增 `scenes`、`epistemic_assertions`、`context_assembly_runs` 等持久化结构。

## 7. 适配器策略

### Character Card

- 继续以 V2 为权威输出格式。
- V3 仓库目前仍以 proposal 表述，不应为追新而迁移核心模型。参考：[Character Card V2](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/README.md)、[Character Card V3 proposal](https://github.com/kwaroran/character-card-spec-v3/blob/main/README.md)。
- 卡片只承载稳定角色核心和必要入口信息；不可把整套知识库都塞进卡片。

### SillyTavern World Info

- 第一版优先导出可解释的关键词、作用域、顺序、概率和预算设置。
- 中文条目需要专门验证关键词边界，不能照搬英文 whole-word 假设。
- 向量召回作为可选增强，并在回放中记录实际命中；不能让它成为唯一触发机制。

### Skill / 长期记忆

继续保留为后续可选运行时，不作为下一阶段前置条件。它必须消费同一装配策略和回执协议，不能复制一套新真源。

## 8. 评测框架

评测拆成五层，避免端到端分数掩盖根因：

1. **抽取层**：事实、实体、关系、来源跨度是否正确。
2. **边界层**：场景起止、入口前后、有效区间是否正确。
3. **投影层**：世界真相、读者公开和角色认知是否分离正确。
4. **检索/装配层**：应召回内容、禁入内容、冲突处理和预算裁剪是否正确。
5. **行为层**：角色一致性、剧情时点一致性、引用根据、拒答和多轮稳定性。

人工审核集是金标准，LLM 裁判只能做扩展检查，并应先与人工结果校准。

### 8.1 必须覆盖的负例

- 问角色尚未知道的未来事件，应不知道、回避或按当时错误认知回答。
- 问从未在作品中出现的信息，应承认缺乏依据。
- 同一事实被后续纠正时，入口前后答案应变化。
- 谣言、误解和真相同时存在时，不应混成单一事实。
- 使用匿名化角色名和改写问题，降低模型预训练记忆作弊。
- 多轮诱导泄密时，权限边界不能逐轮松动。

### 8.2 对照实验

在同一模型、采样参数、场景、问题和评分协议下依次比较：

- A：仅 V2 Character Card。
- B：V2 Card + 原生关键词 World Info。
- C：B + 权限前置的混合检索与重排。
- D：C + 可选长期记忆 / Skill。

每组必须保存回执和真实 API token，用相同夹具可重复回放。先建立人工基线和误差分布，再确定数值门槛，当前不预设看似精确但未经校准的百分比。

## 9. 分阶段推进

### 阶段 0：设计与金标准

- 审批本方案中的概念边界。
- 从真实小说样本选择少量完整场景，而不是随机孤立段落。
- 人工标注场景边界、人物在场、世界真相、读者公开、角色认知和禁入未来信息。
- 写成可回放的正例、负例和更新例。

**退出条件**：团队能够对同一条信息分别回答四个核心问题，且标注分歧有记录。

### 阶段 1：内存合同原型

- 先定义场景快照、认知断言和装配请求/结果的 TypeScript 合同与夹具。
- 在内存中从现有投影生成快照，不迁移数据库。
- 对金标准执行确定性测试。

**退出条件**：概念可表达全部金标准案例，且没有依赖适配器私有规则。

### 阶段 2：Dry-run 装配器与回执

- 实现不调用模型的装配流水线。
- 输出候选、过滤、排序、预算和最终文本预览。
- 用户可以追溯每个片段为何进入或未进入。

**退出条件**：禁入内容零泄漏；错误能定位到投影、检索或预算阶段。

### 阶段 3：SillyTavern 原生回放

- 先接确定性关键词 World Info。
- 用 Prompt Inspector 或等价日志核对实际提示词。
- 比较本项目预期回执与客户端真实装配结果。

**退出条件**：同一测试可复现，差异有明确解释；中文触发行为经过实测。

### 阶段 4：单角色真实 A/B

- 在一个人工已审角色、多个时点上运行 A/B/C。
- 人工主评，自动评分辅评。
- 记录质量、剧透、拒答、延迟和 token 成本。

**退出条件**：新增复杂度对关键错误有稳定、可解释的改善。

### 阶段 5：可选运行时扩展

- 只有 C 相对 B 的收益明确后，才评估 Skill、长期记忆或更复杂代理。
- 所有扩展继续消费统一策略与回执。

## 10. 暂缓项

在阶段 0–4 完成前暂缓：

- 多角色自治代理或多智能体对话；
- 把 GraphRAG 全局查询作为默认路径；
- Character Card V3 迁移；
- 新增更多导出格式；
- 未经实际 Prompt 验证的“一键全自动”；
- 在没有人工金标准时追求单一综合分数。

## 11. 审批前需要回答的问题

1. `reader_disclosure` 是否需要区分叙述视角、章节版本或不同读者频道？
2. 角色认知第一版是否只覆盖 `known / believed / doubted / disbelieved / unknown`，暂不做信心连续值？
3. 场景边界以人工确认优先、模型候选辅助，是否接受？
4. 第一轮真实回放选哪个角色、哪几个明确转折时点？
5. 回执是否允许保存完整最终 prompt；若涉及隐私，保留期限和脱敏规则是什么？

## 12. 推荐决策

批准“先阶段 0、再阶段 1”的方向，但在以上审批问题确认前，不做 schema 迁移、不接新的运行时、不扩展导出格式。

下一份实施文档应只覆盖阶段 0：真实样本的场景金标准规范、标注模板、分歧处理和回放用例清单。它通过评审后，再为阶段 1 制定合同草案。
