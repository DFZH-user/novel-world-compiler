# 阶段三：地点知识图与叙事地图研究及分批实施方案

状态：第一批完成；第二批 A（地点身份治理）完成；第二批 B（模型候选与空间关系审核）完成并通过真实 GLM 小样本验收；第三批核心链路完成；第四批地图/地点世界书、真实坐标审核与 GeoJSON 子集完成

## 1. 决策

阶段三优先做地点知识图和叙事地图，不先做头像/PNG 卡或可直接游玩的整合包。当前事件层已经保存地点字符串，但没有地点身份、别名、层级、空间关系与独立证据审核；直接生成完整世界书或游玩包会把同地异名、同名异地和模型归一化错误固化到成品。

地图首先是“有证据的叙事空间拓扑”，不是看似精确的地理底图。小说只说“客栈在青石镇”“沿官道向北到城门”时，系统保存包含、连接和相对方向；没有原文坐标时不编造经纬度、比例尺或距离。

## 2. 标准与技术取舍

### GeoJSON 只作为可选后续导出

[RFC 7946](https://www.rfc-editor.org/info/rfc7946/) 规定 GeoJSON 使用 WGS84 十进制度坐标，并且标准本身没有不确定性参数。它适合原文明确对应现实地点或用户人工给出坐标的记录，不适合当前大量虚构、相对和模糊空间。第一批不把布局坐标伪装成 GeoJSON 地理坐标。

### 复用 Cytoscape.js

[Cytoscape.js 官方文档](https://js.cytoscape.org/) 支持 compound node、父子层级和图布局。阶段二已经验证其桌面打包、交互和大图降级能力；阶段三继续复用同一引擎，用复合节点表达“房间属于建筑、建筑属于城镇”，避免维护第二套渲染事实。

### 不确定性是一等字段

文学空间研究强调虚构地点数据内在不确定，空间知识图也适合表达拓扑关系与邻接推理。系统因此分开保存原文表面名、规范地点身份、关系真实性、置信度和审核状态；任何推导关系必须能追溯到直接关系，不能冒充原文明示。

参考：

- Grounding Characters and Places in Narrative Texts：https://arxiv.org/abs/2305.17561
- Mapping Literature: Visualisation of Spatial Uncertainty in Fiction：https://doi.org/10.1179/1743277411Y.0000000023
- Spatial scene knowledge graphs with topological relations：https://doi.org/10.1111/tgis.12911

## 3. 数据模型底线

- 地点身份按小说版本隔离；地点别名不能直接成为地图节点。
- 地点提及必须引用当前版本段落，并保存原文字符串与段落内字符范围。
- 已确认事件中的地点字符串只能生成待审核地点候选，不能自动成为已确认地点。
- 同名地点不自动合并；合并、拆分和 cannot-link 在后续审核批次实现。
- 空间关系端点必须是两个不同的已确认地点，并至少有一条可对齐原文的支持证据。
- `contains`、方向、邻接、道路连接和远近都是独立断言；逆关系和传递关系只作为可重建投影，不写回原始事实。
- 地点与空间关系都保存首次揭示位置；面向进入位置的地图继续使用统一防剧透围栏。
- 布局坐标属于可重建视图状态；只有原文或用户明确提供的坐标才属于事实。

## 4. 分批实现

### 第一批：schema v16 地点事实底座

- 地点身份、别名、逐字提及。
- 空间关系候选/正式断言及各自证据表，为方向、拓扑、连接、距离和层级预留稳定结构。
- 从已确认事件地点中本地生成待审核地点候选；必须重新对齐事件证据段落。
- 地点列表、证据浏览、类型修正和确认/排除服务；迁移、事务与幂等测试。

### 第二批：模型抽取与地点审核台

- 分块任务只接收已确认人物、事件、地点别名和当前段落。
- 模型提出地点别名、同名异地和空间关系候选；本地 ID、原文范围和关系端点门禁后才保存。
- React 审核台支持地点合并/拆分、类型修正、关系确认/排除和证据案卷。

### 第三批：防剧透叙事地图

- Cytoscape compound node 展示层级，边编码包含、邻接、方向、通路和远近。
- 进入位置滑块、地点搜索、人物/事件在地点上的叙事轨迹、路径查询和不确定性显示。
- 不把力导向布局解释成现实方向或距离；明确区分“拓扑视图”和“有坐标地图”。

### 第四批：导出与游玩整合

- 版本化 `world_map.json`，所有节点、边和摘要保留来源证据 ID。
- 对具备真实/人工坐标的子集提供 GeoJSON，不为缺失坐标补造数值。
- 将已确认地点、关系社区和进入位置状态合并为完整 SillyTavern 世界书，并支持角色卡 `character_book` 绑定。
- 完成大图性能、备份恢复、安装/便携启动和回滚验收后发布下一版本。

- 导出不会保存 Cytoscape 自动布局位置，也没有 `coordinates` 字段。未来失效事件、推理说明、来源人物、别名与证据沿用统一投影的字段级防剧透裁剪。
- 新增 SillyTavern 地点世界书：每个地点以规范名和当前可见别名作为触发词，汇总类型、父级、当前空间关系和已揭示地点事件；每条当前有效空间关系另建可追溯条目。
- 地点世界书条目扩展保存 `source_place_ids`、`source_relation_ids`、`source_evidence_ids` 与 `source_event_ids`，顶层保存地图来源指纹和进入位置，可从导出成品重建来源。
- 两类导出均使用临时文件加原子改名，格式 Schema、SHA256、别名触发词、来源 ID 和 Electron 保存对话框已经通过自动验收。
- 下一步：设计只允许 WGS84 真实地点或人工录入坐标的数据与审核层；在没有这层明确来源前不提供 GeoJSON，继续避免把图布局冒充地理坐标。

## 14. 第四批第三步：案例复核、真实坐标审核与 GeoJSON（2026-08-30）

### 国内外案例复核

- [Recogito](https://recogito.pelagios.org/help/tutorial) 把文本地点识别、地名库候选和人工确认分开；找不到合适匹配时允许标记，而不是强行落点。其下载页只把 confirmed geo-located places 导出为 GeoJSON。本项目据此坚持“候选不能直接进入地理导出”。
- [Linked Places Format](https://github.com/LinkedPasts/linked-places-format) 使用 GeoJSON-LD FeatureCollection，允许未知 geometry 为 `null`，并把 geometry certainty、名称/几何引用和时间范围放在独立字段。本项目 v19 首先吸收几何确定性与来源引用；多时段几何留到后续版本。
- [World Historical Gazetteer](https://whgazetteer.org/about/) 把地点、历史名称和来源记录分开，强调跨时间、语言连接地点。项目说明进一步采用“来源在某时如此称呼和定位”的 attestations，而非把自动结果声明为唯一真相。本项目因此把来源与人工审核保存在几何记录上。
- [Knight Lab StoryMapJS](https://github.com/NUKnightLab/StoryMapJS) 用地点和幻灯片顺序讲述故事，路线与历史线属于展示配置。本项目继续让人物轨迹/叙事顺序停留在 topology 展示层，不将其写成地理道路。
- [CHGIS](https://chgis.fas.harvard.edu/) 与其 temporal gazetteer 将历史地点、异体名称和多来源数据组织为可连接资源；[浙大学术地图](https://libdb.zju.edu.cn/s/lib/libtb/show/1635) 则把经纬度数据点、人物行迹图和社会关系图作为不同成果类型。本项目据此分离真实坐标、人物事件序列和空间关系图。
- 中国现代文学馆的[中国文学地图](https://www.wxg.org.cn/gxsd/5137.jhtml) 把文学地标扩展为文学、地理与文旅数字展项；南京的[文学地图实践](https://wl.nanjing.gov.cn/wyjxh/zjxh/xhdt/202604/t20260417_5825783.html) 也强调文学世界与真实城市地理的叠加。项目只把真实地理作为可展开的第二层，不取代小说内部空间事实。
- [RFC 7946](https://www.rfc-editor.org/info/rfc7946/) 继续作为交换格式底线：WGS84、Point 坐标为 `[longitude, latitude]`，确定性和来源写在 Feature properties，不能改变 GeoJSON 核心语义。

### v19 实现边界

- 新增 `place_geometries`，v1 每个 revision/place 保存一个首选 WGS84 Point；`source_kind` 为 `manual` 或 `gazetteer`，`certainty` 为 `certain`、`less_certain` 或 `uncertain`。
- 只有已确认地点可登记坐标。保存或修改后状态固定回到 pending；人工再次确认后才进入导出。地名库来源在确认时必须同时具备来源名称和 HTTP(S) 记录链接。
- 不自动调用地理编码服务，不把模型输出、小说相对方位、虚构世界画布点或 Cytoscape 位置写入表中；不知道就保持无坐标。
- 地点案卷提供经纬度、来源、确定性、链接和备注表单，并显示未登记/待审核/已确认/已驳回状态。
- GeoJSON 是防剧透子集：先使用统一叙事地图投影裁剪当前可见地点，再与 confirmed geometry 相交。未确认、未来揭示和无坐标地点均不进入 FeatureCollection。
- 顶层使用 RFC 允许的 foreign member 保存工程、revision、schema/spec、阅读围栏、坐标语义和来源指纹；文件使用临时写入后原子改名并返回 SHA256。
- 首版只支持 Point，不支持 Polygon、LineString、历史时段几何或多个互斥候选。后续若接入地名库，应继续沿用候选/确认门禁，而不是直接覆盖人工记录。

### 验收

- 集成测试覆盖未确认地点拒绝、经纬度边界、编辑后回退待审、地名库来源链接门禁、阅读围栏、confirmed-only、坐标顺序、bbox、格式解析、原子文件与 SHA256。
- Electron 实际流程覆盖定位地点、填写坐标、保存待审、确认并导出 `.geojson`；文件核对得到一个 WGS84 Point Feature。
