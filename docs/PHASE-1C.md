# 阶段 1C 批次 1：事实整理与人物状态变化

## 分层原则

阶段 1C 不改写阶段 1B 的原始事实。当前数据分为：

1. `character_facts`：模型或用户得到的原始主张及证据；
2. `character_fact_clusters`：规范化后代表同一事实值的簇；
3. `character_fact_relations`：同一人物、同一属性出现不同值时的关系候选；
4. `character_state_transitions`：用户确认“状态变化”后产生的转换。

任何关系候选都不能删除、覆盖或偷偷改写原始事实。

## 当前自动归组边界

本批只自动归组规范化后完全相同的类别、谓词和值。规范化包括 Unicode NFKC、大小写、空白和标点统一。

例如“客栈”与“客 栈。”可以进入同一簇；“客栈内”与“客栈”不会因为语义相近而自动合并。语义归一会留到后续可审核的模型批次。

每个事实簇保留全部原始成员、来源方式、真实性状态、审核状态和证据数量。

## 同属性不同值

同一人物、同一类别和规范谓词出现不同值时，系统生成关系候选。当前本地建议规则包括：

- 两条事实带有不重叠的明确生效区间：建议“不同阶段并存”；
- 较早事实来自传闻、他人陈述、主观看法或存疑主张，较晚事实由旁白断言：建议“传闻被纠正”；
- 地点、阵营、职业、身份、伤势、等级、关系等可变属性出现不同值：建议“状态变化”；
- 其余情况：保持“需要判断”。

这些只作为候选。用户可以将实际关系分类为：

- 真正矛盾；
- 状态变化；
- 不同阶段并存；
- 人物观点不同；
- 传闻被纠正；
- 身份伪装；
- 彼此无关。

## 状态变化

只有关系被人工确认为“状态变化”后，系统才生成 `from_value → to_value` 转换，并保存：

- 人物、类别和属性；
- 前值与后值；
- 两个事实簇；
- 两边首次原文观察段落；
- 后值最早证据段落作为触发证据；
- 关系置信度。

把关系恢复为待审核或排除时，相应转换会被删除，但事实簇和原始事实仍保留。

## 当前边界

- 本批完全在本机执行，不调用 API。
- 当前转换顺序是“原文观察顺序”，不是完整的故事内时间；倒叙和插叙要等时间线阶段处理。
- 当前不会自动判断语义近似谓词，例如“所在地”和“所处位置”。
- 多值属性可能产生大量关系候选，因此默认必须人工判断。
- 人物合并、拆分或撤销后会清空派生事实簇、关系和转换，按最新人物身份重新整理，原始事实不受影响。

## 批次 1 当时的后续路线

1. 增加可审核的谓词词典和语义近似归一。
2. 给大量关系候选增加可选模型分类，但仍要求证据和审核。
3. 抽取故事内事件与时间表达，将原文观察顺序转换为故事时间偏序（已在批次 2–4 完成首版）。
4. 按选定进入时间计算人物当时的有效状态（已在批次 5 完成首版）。

## 批次 2：时间证据与 v9 底座

本批新增“故事时间”工作区，但还没有把识别结果称为完整时间线。当前层只负责保存可追溯的时间证据：

- 明确日期、时刻、相对时间、持续时间、频率、年龄、季节与时代纪年分别存储；
- 每条结果保留段落、字符范围、规则/模型/人工来源、置信度和审核状态；
- 可以确认、排除、恢复或人工修正规范时间值；
- “翌日”“三日后”“与此同时”等只保存相对语义，等待连接到事件后再确定锚点；
- 扫描排除用户标记为不参与分析的段落，重复扫描不会复制结果，也不会覆盖已经审核的值。

schema v9 同时建立后续事件层所需的表：事件、参与人物、地点、事件证据、事件—时间连接和事件间时间关系。事件关系支持 `before`、`after`、`simultaneous`、`includes`、`is_included` 与 `unknown`，但本批尚不自动生成这些关系。

批次 2 发布时，旧 v8 工程会以新增表方式升级到 v9；当前批次继续只增表升级到 v10。已有原文、人物、事实、对白和审核结果不被改写，工程清单只在数据库成功打开并校验后更新。

## 批次 3：事件抽取本地数据层

schema v10 增加可恢复的事件抽取运行、逐分块结果和事件来源映射。当前已经完成从结构化事件输出到本地数据库的完整验证链：

- 事件必须至少有一条来自核心分块的支持证据；
- 引用必须能在指定段落逐字或规范化对齐，否则整个无证事件不会入库；
- 参与人物只接受当前工程中未排除的人物 ID，错误 ID 降级为未归并原文名；
- 时间连接只接受当前版本中未排除的时间表达；
- 地点、参与人、时间连接和证据分别保存，任何一层都不覆盖原文；
- 同一事件按类型、标题和全部支持证据生成稳定指纹，重复运行不会复制事件或覆盖人工审核；
- 分块失败可按同一输入哈希恢复，已完成分块不重复处理。

桌面“故事时间”页能够启动、显示和审核候选事件及其人物、地点、原文证据。用户已明确允许在主动点击时把当前小说分块发送到所配置的 API；界面仍会在每次启动前再次说明并确认。API 返回的 JSON 不会直接成为事实，必须先通过本地 ID 范围与原文证据门禁。

真实 DeepSeek 最小连通验证使用一句虚构测试文本完成，没有上传用户小说：请求 `deepseek-chat`，服务返回当前 `deepseek-v4-flash`，得到 1 个结构化事件且证据逐字对齐；本次消耗 93 个输入 Token、44 个输出 Token。密钥未写入工程、测试、日志或源码。

## 批次 4：可审核的事件时间关系图

schema v11 把“系统建议”和“人工决定”分开保存。系统只为原文观察顺序相邻的事件建立线性数量的候选，避免长篇小说产生全事件两两组合：

- 两端都有完整明确日期时，可建议 `before` 或 `after`；
- 后一事件连接“翌日、三日后、随后”等相对时间时，可建议前一事件 `before` 后一事件，但仍说明相邻事件只是待审核锚点；
- “与此同时、同时”可建议 `simultaneous`；
- 没有可靠时间线索时生成 `unknown`，明确提示叙述顺序不等于故事时间。

用户确认关系前必须先确认两端事件。确认 `before`、`after` 或 `simultaneous` 时，系统先合并同时事件组并检查有向时间图；如果新决定形成闭环，就拒绝该决定且不改变原候选。

当前时间轴输出包括：拓扑层级、同时事件组、是否已有关系约束和原文观察位置。`includes` / `is_included` 作为区间包含关系保留，但不会被错误转换为先后边；未约束事件不会获得伪造日期或伪造顺序。

## 批次 5：进入时间的人物状态快照

用户可以从已确认事件中选择进入点。快照计算完全在本地完成，只读取以下审核结果：

- `character_facts.review_status = confirmed` 的人物事实；
- 两端事实簇都包含已确认事实，且事实关系已确认为 `state_change` 的状态变化；
- 已确认的触发事件及其逐字证据段落；
- 已确认的事件时间关系和人工修正结果。

状态变化的触发段落通过事件证据连接到事件。确认时间图能证明触发事件早于或同时于进入事件时采用后值；能证明进入事件早于触发事件时采用前值。没有状态变化且只有一个已确认值的属性作为“当前唯一确认值”。

以下情况不会猜测：触发段落没有连接到已确认事件、触发事件与进入事件在时间图中断开、多个变化无法判断最后或最早生效者、同属性存在多个确认值但没有确认的变化关系。它们统一输出 `ambiguous`，保留可能值和中文原因。

当前快照中的 `public`、`private`、`secret` 仍是事实抽取阶段的故事内可见性，不是“哪个人物知道什么”的知识图谱。人物知情状态需要后续单独建立信息传播与目击关系，不能从当前可见性字段直接推断。
